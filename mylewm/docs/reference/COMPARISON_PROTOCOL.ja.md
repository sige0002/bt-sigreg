# BT-SIGRegの比較評価を蓄積する手順

方針更新：2026-09-16。現在の目的は、**小型世界モデルの学習で、BT-SIGRegがRaw／TCに対して何を改善するかを確かめること**。CEMの改良やBC方策の調整を主実験に置き換えない。先のCEM診断で提案した探索改善より、既存結果の整理と条件を揃えた比較を優先する。

[既存実験の一覧](../reports/EXPERIMENTS.ja.md) → この手順で比較条件を決める → [学習](../TRAINING.ja.md)・[評価の操作](../EVALUATION.ja.md) → [検証状況](../reports/VALIDATION.ja.md)へ反映する。ここに計画を記載したことは、新規学習・追加評価・停止中run再開の承認ではない。実行はユーザーの明示依頼がある範囲で行う。

## 何を比較するか

| 区分 | 比較 | 得られる結論 |
|---|---|---|
| 主比較 | 同じ共有基盤・データ・予算でRaw／TC／BTを学習し、同じCEMで評価 | 正則化方式による差を調べる |
| 公式モデルとの参考比較 | 公式LeWM checkpointとローカルBTを、可能な限り同じ評価器で評価 | 既存モデルに対する到達水準。学習条件が違えばBTの効果は同定できない |
| 同一runの途中比較 | 同じ学習runの複数checkpoint | 更新を重ねた効果。Raw対BTの比較ではない |
| 補助診断 | 保持デモ予測、行動入替、候補順位、尺度対照 | 主比較の結果を解釈する材料 |
| 視覚表現の補助評価 | 凍結encoder＋BC | 表現を行動模倣に利用できるか。未来予測器による制御ではない |

Rawはzへ直接SIGReg、TCは時間残差へSIGReg、BTは学習専用の有界可逆写像T(z)へSIGRegを適用する。E・P・A・Fの構成と予測損失は共有する。推論・Goal距離はzを使い、Tは使わない。[アルゴリズム](../ALGORITHM.ja.md)

**BCを付けることは世界モデル評価の必須工程ではない。** BCの生成行動誤差とBCの環境成功率も別指標である。依頼・レポートでは「世界モデル＋CEM」「世界モデルの予測診断」「BC生成行動」「BC環境成功率」と具体的に表記する。

## 1. 既存runから使えるものを選ぶ

[実験一覧](../reports/EXPERIMENTS.ja.md)からcheckpoint・設定・結果を確認し、次の判定を行う。

- **そのまま主比較に使える**：共通モデル初期値、データ、更新予算、前処理、評価条件、完了証拠が一致する。
- **評価を揃えれば参考比較に使える**：重みはあるが学習条件が異なる。再評価しても学習条件差は消えない。
- **復元・検証が必要**：古いパス、結果ファイル欠落、旧依存、失敗した描画監査がある。記録を現在の存在証拠としない。
- **不足する対照**：適合するRaw／TCなどがない。条件を決めた上で新規学習の対象とする。

「同じseed」「同じ100k」という名前だけでは一致と判定しない。実config・manifest・checkpoint hash・ソース・依存・学習バッチ抽出法を照合する。旧RBG／旧Frobenius版は現行Cayley v2のBT結果に含めない。停止維持のrunを対照が足りないという理由で再開しない。

## 2. 共通条件を先に固定する

各比較につき、以下を1つの比較仕様として実行前に記録する。方式ごとに評価設定を選び直さない。

| 対象 | 揃える内容 |
|---|---|
| データ | データ版・由来・分割・train-only統計・入力解像度・カメラ・履歴・行動の時刻対応 |
| モデル | 共通E/P/A/Fの構成・実初期値hash。BTのTは追加分として別記 |
| 学習 | batch、提示クリップ数、抽出法・順序、更新数、LRと添字、warmup、optimizer、精度、augmentation、seed |
| 制御 | Goal、物理初期状態と画像、成功関数、CEM候補数・反復数・elite数・候補分布、horizon、実行行動数、予算、settling、seed |
| 実行環境 | ソース・依存・デバイス・描画backend・実測解像度。相違があるなら影響と比較の格下げを記録 |
| 選択規則 | 最終checkpointか、共通の検証規則で選ぶか。評価用test成功率で都合のよいcheckpointを選ばない |

同じ更新数と同じ実時間は別の予算である。まず同じ更新・提示数で比較し、Tの追加パラメータ、時間、メモリを報告する。同じ実時間の比較をする場合は別表にする。方式固有の調整を行う場合も、検証集合と調整予算を揃え、主比較と分ける。

既存PushT100k、旧LIBERO100k、新LIBERO10kの予算は混ぜない。新LIBERO10kのBTを利用するなら、Raw／TCも同じ再生成データ・同じレシピの10kを候補とする。共通初期値等を再現できなければ、BTを含む一式を新規に揃える。ここで10k／100kの追加学習を自動決定しない。

## 3. PushTから比較を組む

2026-09-16の実行指定：RawとBTを各140,000更新で同時学習する。[固定条件と起動記録](../reports/PUSHT_RAW_BT_140K.ja.md)。公開コードに合わせたクリップ分割は、episode単位の保持検証とは区別する。

論文のPushT学習予算は10 epochs。Figure 18の曲線は約18万更新までを示す（図からの概数）。公開コードの100 epochs既定値や既存ローカル100kと区別する。[一次資料と更新数の扱い](LEWM_TRAINER_NOTES.ja.md#a4-本学習の予算を選ぶ)。同じ10 epochsでも窓抽出等で更新数が変わるため、実DataLoader長と提示数を照合する。

最初に既存LeWM・Raw・BTの重みと評価条件を棚卸しする。公式重みとの参考比較を整えつつ、方式差を見る主比較を作る。

1. 同じ学習経路でRawとBTの条件を固定する。現在の`mylewm.training.train`は`--mode raw|bt`対応。**このCLIにTCは未対応**なので、`--mode tc`を使える前提の手順を書かない。TC追加は別の実装・回帰確認が必要。
2. 固定ケース・CEM・物理行動分布を揃えて評価する。最初の接続確認と最終成績のケースを区別し、主集計は保持ケースで行う。
3. 同じケースでの成功率差、片方だけ成功するケース、失敗動作、時間を報告する。開始画像だけでなく物理初期状態も照合する。
4. 既存の固定200ケース、別の50ケース、train由来ケースを混ぜない。ケース定義と分割由来を集計表に付ける。

操作は[PushT評価手順](CEM_AND_RENDERING.ja.md#pusht)、学習は[PushT手順](DATASET_RECIPES.ja.md#hdf5-pusht-training)。過去のRaw70kとBT70kには学習経路・初期物理状態差があり、すでに主比較が完成しているとは扱わない。

## 4. LIBERO-10でマルチタスクを確かめる

10タスク共有のRaw／TC／BTを、同じデータ版・レシピで比較する。`mylewm.training.train_libero train`は3方式に対応している。

- 保持デモで予測誤差、無変化対照との比、正しい行動と入替・ゼロ行動の差を測る。時刻・教師画像・乱数を揃える。
- 世界モデル＋固定CEMで環境成功率を測る。全10タスクの平均・各タスク・下位タスクを報告する。途中まで終わったタスクの合算を最終平均としない。
- 候補の予測／実測順位は補助診断とする。32行動の分岐実験を、長いタスクの通し成功率とは呼ばない。

新256pxデータでは描画・前処理の対応を先に確認する。BC評価器とnative診断の256px対応があることは、通しCEM評価器全体の対応を保証しない。使用する経路ごとに[評価ガイド](../EVALUATION.ja.md)の監査を通す。

方式間でzの尺度や座標が違うため、生の潜在MSEだけで順位付けしない。無変化対照、分散・尺度の診断、必要なアフィン対照を併記し、最終的な制御成績と合わせる。低いMSEや非崩壊を、操作に必要な情報の保存保証としない。

## 5. 他のLeWM環境を追加する判断

2026-09-16追記：ユーザー指定によりOGBench Cube single expertはLeWM設定に揃える。[データ準備・学習・評価手順](OGBENCH_WORKFLOW.ja.md)を参照。手順追加と実行完了を区別する。

`lewm/config/`にはReacher・TwoRoom・Cube等の設定がある。ただし設定ファイルの存在は、ローカルの学習・評価完了の証拠ではない。現在の実施記録の中心はPushTとLIBERO-10である。

追加環境を採用する場合は、データと公式重みの入手、環境起動、前処理・行動・Goal・成功関数、共通Raw／TC／BT経路、完了済みrunの有無を先に確認する。接続確認→公式モデルの再現確認→同予算の方式比較の順に進む。PushT／LIBEROの比較が揃わないまま環境だけを増やさない。新規環境の追加学習・評価は別途依頼の範囲で実施する。

## 6. 結果の保存と報告

1つの比較に、比較仕様・方式別run参照・checkpoint hash・評価条件・ケース別結果・完了照合・集計スクリプトを紐付ける。生のrun証拠は書き換えず、集計は新しい出力に保存する。通常の起動検証はデータのサイズ・mtimeで、全量hash再計算は明示指定時のみ。

主結果の表には、環境、方式、データ／分割、学習seed、更新数と提示数、checkpoint選択規則、制御条件、試行数、成功率と区間、学習／推論時間、追加計算量、比較上の制約を載せる。停止・失敗・未評価を成功率0へ置換しない。

単一seedは予備結果とし、複数の独立学習seedで平均とばらつきを確認する（初期計画の目安は3seed）。同じ初期状態を共有する場合は対応付きの差を使い、試行の不確実性と学習seedの不確実性を分ける。LIBEROはタスクを均等に集計し、少数の得意タスクで全体を説明しない。

終了コード、`status.json`、結果数、実プロセスを照合してから完了とする。レポートを[実験一覧](../reports/EXPERIMENTS.ja.md)へ追加し、[検証状況](../reports/VALIDATION.ja.md)には現在言える結論と不足だけを更新する。日付順の詳細経緯は個別レポートへ置く。
